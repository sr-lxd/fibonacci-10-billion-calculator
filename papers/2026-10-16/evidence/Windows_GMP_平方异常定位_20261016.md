# Windows GMP 超大整数平方异常：复现与定位

制作日期：2026年10月16日

## 已确认的故障性质

2026年10月15日，原程序在 Windows 的 gmpy2 2.3.1/GMP 6.3.0 下计算 F(8,000,000,000) 时，两次都停在最后一层第一次平方。操作数为 2,776,967,654 位。stderr 显示 `GNU MP: Cannot allocate memory (size=4294597664)`，退出码为 3。另以 gmpy2 2.2.1 的隔离安装包重复两次，失败位置和报错相同。原程序此时尚未进入十进制转换。

在导入 gmpy2 前安装的 GMP 分配回调记录了完整的 64 位 `size_t` 参数，并原样转交旧分配器。该次分配请求实际为 **18,446,744,073,709,181,984 字节**，等于 `2^64−369,632`。它的低 32 位恰好是 **4,294,597,664**，与 stderr 所示数字一致。原报错不能解释为一次正常的约 4 GiB 内存申请，更不能据此宣称 GMP 存在普遍的 4 GiB 内存上限。

2026年10月16日又将问题缩小到单次平方。诊断程序只构造 `2^(b−1)` 并平方，没有运行斐波那契递推或十进制输出。它在一次性子进程中运行，父进程每 50 ms 采样内存，并设置超时和可用内存保护。

| 路径 | 操作数位数 b | 结果 | 分配回调中的异常请求 |
|---|---:|---|---:|
| gmpy2.square | 1,000,000,000 | 成功 | 无 |
| gmpy2.square | 2,000,000,000 | 成功 | 无 |
| gmpy2.square | 2,100,000,000 | 成功 | 无 |
| gmpy2.square | 2,140,000,000 | 成功 | 无 |
| gmpy2.square | 2,147,483,647 | 退出码 3 | `2^64−523,552` |
| gmpy2.square | 2,776,967,654 | 退出码 3 | `2^64−369,632` |
| 直接调用同一 GMP DLL 的 mpz_mul | 2,140,000,000 | 成功 | 无 |
| 直接调用同一 GMP DLL 的 mpz_mul | 2,147,483,647 | 退出码 3 | `2^64−523,552` |

直接调用测试通过 `ctypes` 调用该 DLL 的 `__gmpz_init_set_ui`、`__gmpz_mul_2exp` 和 `__gmpz_mul`，不导入 gmpy2。先用 1,000 位输入验证结构体布局与调用约定。失败点的最低实测可用物理内存仍超过 21 GiB；没有触发父进程保护。位数为 2,147,483,647 的平方结果按数学性质只需 4,294,967,293 位，即约 512 MiB 的结果位串；接近 `2^64` 字节的申请显然不是结果本身的正常存储需求。

因此，现有实验已经把性质定位为：**这份 Windows GMP DLL 在超大整数平方路径中产生了接近无符号 64 位上限的异常分配尺寸，并因此中止。** 异常数值具有负值转换为 `size_t` 或整数回绕的典型形状。成功和失败输入又夹在 2,140,000,000 至 2,147,483,647 位之间，接近 32 位边界。随包头文件在 Windows 上把 `mp_bitcnt_t` 声明为 `unsigned long int`、`mp_size_t` 声明为 `long int`，二者均为 32 位。这些线索支持检查长度或工作区计算中的窄整数，但**还没有证明具体是哪个 GMP 表达式、哪个乘法分支发生了溢出**。不能仅凭“接近 2^31”就指定 FFT 为根因。

## 下一步如何定位源码表达式

1. **固定二进制来源。** 保留失败 DLL、gmpy2 模块、wheel、头文件的哈希和构建信息。先确认调试构建与现有 DLL 的 ABI、GMP 版本、CPU 调优及乘法阈值一致。只比较标为 GMP 6.3.0 的不同构建，不能单独归因于 Windows 或 Linux。
2. **采用独立的原生 C 复现器。** 直接链接这份 DLL，构造 `2^(b−1)` 并调用 `mpz_mul(y,x,x)`。与本次 `ctypes` 测试核对同样的成功/失败位数，再排除 Python 与绑定层。设置可用内存和运行时长保护；每次用独立进程，预期失败允许非零退出。
3. **在分配入口截获异常数值。** 用全宽 `size_t` 记录 `allocate/reallocate` 的新尺寸、旧尺寸和原生调用栈。只记录并终止异常请求，不把返回 `NULL`、抛 Python 异常或 `longjmp` 当作恢复手段。GMP 文档说明其分配函数若返回就必须完成分配，失败恢复没有定义。
4. **使用带符号的相同配置 GMP 构建。** 在异常请求产生前设条件断点，沿 `mpz_mul → mpn_sqr/相关乘法分支 → 工作区计算` 回溯，记录每一步操作数类型、位宽和数值。比较 2,140,000,000 位成功样本与 2,147,483,647 位失败样本，找出第一个从合理正值变成负值、回绕值或不合理大值的表达式。若重编后阈值改变，应先解释配置差异，不能把新构建的栈直接归到原 DLL。
5. **做针对性验证。** 试同位数但不同内容的操作数、`mpz_mul(x,x)` 与独立目的变量、不同 GMP 构建，以及关闭某个乘法分支的调试构建。只有在调用栈、源码表达式与边界实验相互吻合后，才把具体根因写入论文。随后以原始 DLL 和修复 DLL 各跑一次边界输入，并保留输出校验。

## 旧问题如何避开

- 不把 stderr 中的 `4,294,597,664` 当作完整申请。先读全宽 `size_t`。
- 不在原程序主进程中尝试捕获 GMP 的致命分配失败。用子进程保存退出码、stderr、内存采样和分配回调记录。
- 不用“可用内存很多”单独推断溢出。核心证据是回调中的 `2^64−k` 异常尺寸和单次平方复现。
- 不把 WSL2 成功解释为操作系统单变量实验；Linux 的 GMP 二进制构建也不同。
- 不再跑完整百亿项及十进制输出寻找这一故障。单次稀疏整数平方已在约 6 秒内复现失败。
